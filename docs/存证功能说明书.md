## 1. 概述（一页读懂）

**非默（The Unmuted）** 是一款面向性侵、家庭暴力、跟踪骚扰等侵害的幸存者的双语（中/英）安全应用。存证功能是产品的核心：**帮助用户在事发当下或事后，把私密的证据材料加密保存起来，并在未来有需要的时候（报警、申请保护令、诉讼）能够取出并作为有效证据进行举证。**

存证功能由三个环节构成一条完整闭环：

```
取证（现场拍摄/录音/导入） → 存证（端到端加密保存云端） → 举证（一键导出可独立验证的证据包）
```

三个最重要的设计事实：

1. **服务器零明文。** 所有文件在离开用户设备**之前**就已用 AES-256-GCM 加密，云端只保存密文。服务器运营方（包括我们自己）在技术上无法查看任何证据内容。
2. **完整性可独立验证。** 每份证据在取证瞬间即在设备本地计算 SHA-256 文件指纹并固定，配合设备与服务器双时间戳。导出的举证包用通用工具（Windows certutil / macOS shasum）即可验证，**不依赖非默应用本身继续存在**。
3. **诚实原则。** 我们不夸大任何安全承诺。当前版本尚未接入权威时间戳（TSA）服务——数据结构已为将来"补锚定"预留（见第 8、10 章），但在接入之前，我们不对外宣称任何形式的"区块链存证"或"司法级认证"。

## 2. 背景：为什么需要电子存证

性侵、家暴、骚扰类侵害有两个证据难题：

1. **证据产生在私密场合**，往往只有电子形式（照片、录音、聊天记录、伤情照片），且转瞬即逝；
2. **受害者常与施暴者同处一室**，手机相册、聊天记录随时可能被翻查、被胁迫删除。

在法律层面（背景介绍，非法律意见）：

- 《中华人民共和国民事诉讼法》将**电子数据**列为法定证据类型之一；
- 最高人民法院《关于民事诉讼证据的若干规定》（2019 年修正）对电子数据的范围和真实性审查作出了细化规定，法院审查电子数据真实性时会考虑其**生成、存储、传输所依赖的方法是否可靠、内容是否完整、是否可以通过特定形式得到验证**等因素；
- 《中华人民共和国反家庭暴力法》（2016 年施行）确立了**公安告诫书**和**人身安全保护令**制度，二者的申请都需要证据支撑。

非默的存证设计正是对准上述审查要点：**指纹固定证明"内容未被改动"，双时间戳证明"何时存在"，取证分级诚实说明"如何产生"**——同时用端到端加密解决"证据放在哪里才不会被发现、被删除"的现实问题。

## 3. 产品设计原则

存证相关的每一个技术决策都服从以下三条原则（优先级从高到低）：

### 3.1 幸存者隐私与安全优先于一切（包括开发便利）
- 紧急联系人、密码等个人数据**只存在用户设备本地**（localStorage），设计上从不上传服务器。威胁模型明确包含"服务器被调取或被攻破"的情形。
- 精确 GPS 坐标只出现在两个地方：用户发给**自己**紧急联系人的求救短信，以及**客户端加密后**的证据元数据。任何共享/公开通道都不允许出现精确坐标。

### 3.2 诚实，不夸大
- 界面文案与对外宣传不允许出现名不副实的安全声明。2026-07-08 我们主动下线了早期演示版的"模拟区块链锚定"相关文案（详见决策记录 D-014 及 Phase 4a 清理）。
- 应用内取证会诚实分级：现场拍摄与事后导入的文件被明确区分标注（见 5.3）。

### 3.3 反胁迫设计
- 施暴者可能胁迫受害者当面删除证据。删除流程在界面上**看起来是彻底的**，实际有 72 小时冷静期，恢复入口隐蔽且需再次验证密码（见 5.8，决策记录 D-022）。

## 4. 功能全景：取证 → 存证 → 举证

| 环节 | 用户做什么 | 系统做什么 | 关键保证 |
|------|-----------|-----------|---------|
| **取证** | 在应用内拍照 / 录像 / 录音，或导入已有文件 | 取证瞬间在设备本地计算 SHA-256 指纹；封存时间、GCJ-02 位置、设备信息等元数据；按来源分级（现场取证 / 事后导入） | 指纹与元数据在任何网络传输之前即已固定 |
| **存证** | 无需额外操作 | 文件用一次性 AES-256-GCM 密钥加密 → 密文上传私有存储桶；文件密钥用主密钥包裹后连同加密元数据存入云端索引 | 云端全程只见密文；断网自动进入待上传队列，恢复后自动重传 |
| **举证** | 一键"导出举证包" | 在设备本地解密原件，连同自包含的双语说明 HTML 打包为标准 ZIP | 用通用工具即可验证指纹，不依赖本应用存在；说明内含分场景维权指引 |

## 5. 用户完整旅程（逐步详解）

### 5.1 注册与账号（账号层）

- 用户输入邮箱，收取 **6 位一次性验证码**（OTP）完成登录。没有传统的"账号密码"——账号层的身份凭证就是邮箱本身，可通过邮箱找回，**账号层不承担数据加密职责**。
- 账号的作用：把加密后的证据索引绑定到一个可跨设备恢复的身份上。换新手机后，用邮箱验证码登录 + 输入保险柜密码，即可在新设备上恢复全部证据访问。

### 5.2 保险柜密码与纸质恢复钥匙（数据层）

首次创建账号后，用户需要：

1. **设置保险柜密码**（最少 8 位）。这个密码**从不发送到服务器**，是解开所有证据的唯一日常钥匙。
2. **抄写纸质恢复钥匙**：系统生成一个 12 位字符的恢复码，按 `XXXX-XXXX-XXXX` 分组便于手抄。**只展示这一次**，用户确认抄写后不再显示。忘记密码时，用恢复钥匙可以解锁并重设密码。

> **诚实代价说明：** 由于服务器只有密文（零知识设计），如果用户**同时**忘记密码和丢失恢复钥匙，任何人（包括我们）都无法恢复其证据。这是端到端加密的固有代价，产品在设置流程中以平实语言向用户说明。

账号层与数据层的关系（决策记录 D-017/D-018）：

```
账号层（能不能登录）：邮箱 OTP —— 服务器可协助找回
数据层（能不能解密）：保险柜密码 / 纸质恢复钥匙 —— 仅存在于用户手中
```

主密钥只保存在内存中，**每次重新打开应用都从锁定状态开始**，需要重新输入密码。

### 5.3 取证：应用内拍摄 / 录音

用户在证据保险柜内直接调用摄像头 / 麦克风取证。取证瞬间，在设备本地完成：

- **计算 SHA-256 文件指纹**（加密与哈希在文件产生后立即执行）；
- **封存元数据**：设备时间（`capturedAt`）、GCJ-02 坐标（进入取证界面时预热定位，含精度）、设备信息（User-Agent）；
- **取证分级**（决策记录 D-019）：
  - **一级 · 现场取证**：应用内直接录制，或经拍摄入口且文件新鲜度 ≤ 2 分钟（`lastModified` 距当前时间）；
  - **二级 · 事后导入**：显式走"导入已有文件"入口，或文件新鲜度超窗。
  - 分级徽章展示在存证回执和历史记录上。**分级是诚实机制**：桌面浏览器会忽略拍摄属性、手机用户可以切到相册选旧图，旧文件的 `lastModified` 会诚实地把它标为二级。

### 5.4 导入已有文件

对于事发时已经拍下的照片/录音，用户可导入。系统同样在导入瞬间本地计算指纹并封存元数据，但明确标为**二级 · 事后导入**，说明中注明"文件本身的生成时间以文件自身属性为准"。

### 5.5 存证：加密与上传

每份证据的加密上传流程（全部在浏览器本地完成加密）：

1. 为该文件生成**一次性 AES-256-GCM 密钥**（256 位）与随机 IV（12 字节）；
2. 加密文件，得到密文与两个指纹：`originalHash`（原文 SHA-256）、`encryptedHash`（密文 SHA-256，下载时校验完整性用）；
3. 用**主密钥**包裹（wrap）该文件密钥；元数据（文件名、备注、时间、坐标、设备）同样用主密钥加密；
4. 密文上传到私有存储桶，路径为 `{用户ID}/{记录ID}`；包裹后的文件密钥 + 加密元数据 + 两个指纹 + 分级 + 设备时间写入云端索引表，服务器同时记下自己的接收时间（**双时间戳**）。

**离线韧性：** 密文始终在设备 IndexedDB 保留本地缓存；断网时记录进入待上传队列，网络恢复（`online` 事件）后自动重传；每条记录带"已同步 / 待上传"徽章。

### 5.6 查看与管理

- **存证记录随时可见，无需输密码**：保险柜未解锁时，记录列表正常显示（时间、取证分级、哈希值等明文字段）；文件名/类型/大小等加密元数据显示为"加密记录"占位。
- **解锁查看 / 导出举证包 · 每次都必须输密码（决策 D-039）**：这两项动作都会把明文文件写出 App 沙盒（落到 Downloads 目录），即使本次会话已经解锁过保险柜，也必须重新验证密码——这样保证即便手机在已登录已解锁状态下被他人拿到，也无法一键把证据原件导出。
- **删除**：保留反胁迫设计（D-022）——若本次会话已解锁，删除仅需简单确认（无需再输密码），确保被胁迫场景下能立即完成表面上的"彻底删除"；若保险柜尚未解锁，则弹出密码框。
- 每条记录显示：文件名（加密，已解锁时可见）、时间、分级徽章、同步状态。
- 旧版演示期的记录（按早期"每文件独立密钥文件"方案加密）以只读方式列出，标注"旧版记录，需要密钥文件"。

### 5.7 举证：一键导出举证包

对任一记录点击"导出举证包"（决策 D-020 + D-039）：

**两步密码：**
1. 先用**保险柜密码**授权本次导出（验证你是账号持有人）；
2. 再为这次导出**新设一个一次性密码**（≥8 位，二次确认），用于加密即将输出的证据文件。这个密码通过短信/电话等安全渠道单独告诉接收人（律师/法官/警方）——**明确提示不要复用保险柜密码**，避免保险柜密码离开设备。

**举证包 ZIP 结构：**

| 文件 | 内容 | 加/明文 |
|------|------|---------|
| `举证说明.html` | 记录元数据、指纹期望值、两步校验指引、分场景维权指引、援助热线 | 明文（法官/律师直接阅读） |
| `解密工具.html` | 自包含 Web Crypto 解密页面（无外链、无依赖，任何现代浏览器离线打开即可用） | 明文 |
| `证据文件/<原文件名>.enc` | 原件密文：`"NMUT"` magic + 版本 + 16B salt + 12B IV + AES-256-GCM 密文；密钥由 PBKDF2-SHA256(export_password, salt, 600k iters) 派生 | **密文** |

**接收人使用流程：**
1. 收到举证包 ZIP + 从发送人处（通过独立渠道）拿到一次性密码；
2. 用任意现代浏览器打开 `解密工具.html`，选中 `.enc` 文件，输入密码，点击"解密并下载" → 原件保存到本机；
3. 打开 `举证说明.html`，按其中 macOS `shasum -a 256` / Windows `certutil -hashfile` 命令校验解密后文件的 SHA-256 指纹与说明中「原始文件指纹」完全一致。

**设计要点：**
- **只用标准格式与标准算法**——ZIP + HTML + Web Crypto API + SHA-256，确保即使非默停止运营、发送/接收双方都无本应用，举证包依然完整可验证。
- **加密体现在哪里**：云端只有密文；导出到本地的 `.enc` 也是密文；一次性密码只用一次，即使接收人电脑被入侵，泄露的也仅限这一次导出的内容，不影响保险柜内其他证据。
- **对被截获场景的抗性**：举证包如通过邮件/微信/网盘转交时被截获，攻击者只拿到密文；密码走独立通道告知，两者分离才能解密。

### 5.8 删除与 72 小时冷静期（反胁迫，决策记录 D-022）

- 删除操作在界面上**呈现为立即且彻底**：成功后仅显示「已删除」，全程不出现"回收站""可恢复"等字样；本地索引与缓存立即清除，设备上查不到任何痕迹。
- 实际为 **72 小时软删除**：云端密文保留 72 小时后由客户端触发彻底清除。
- 恢复入口是记录列表最底部一行不起眼的灰字（「找回误删的记录」），点击后**必须重新输入保险柜密码**才会展示任何内容——即使应用处于已解锁状态。
- **为什么这样设计**：施暴者可能胁迫受害者当面删除证据。删除必须让旁观者信服"已经删干净了"，而受害者本人可以在 72 小时内悄悄恢复。不知道密码的人无法确认任何东西曾被删除或还能恢复。
- 诚实代价：真心想立即彻底删除的用户也要等 72 小时，这是反胁迫保护的交换条件。

### 5.9 紧急求救与存证的关系

紧急求救（SOS）功能与存证账号**完全解耦**：紧急联系人存在设备本地，求救不需要登录、不需要密码。登录/解锁页右下角有一个不带任何文字的 ‼️ 图标（仅在本机已设置过紧急联系人时显示），点击即达长按 2 秒求救按钮——紧急时刻不被密码墙阻拦，同时陌生设备上登录页保持纯净伪装（决策记录 D-024）。

## 6. 安全架构技术详解

*本章面向团队成员与技术尽调，含具体参数与数据结构。*

### 6.1 密钥体系（D-017 密钥层级）

```
保险柜密码 ──┐
             ├── Argon2id（64 MiB、opslimit=2，随机盐）──> KEK（AES-256-GCM）
纸质恢复钥匙 ─┘                                             │
                                                           ▼
                                             解开「密钥盒」得到 主密钥（AES-256-GCM，256 位）
                                                           │
                                                           ▼
                                           包裹每个文件的一次性 AES-256-GCM 文件密钥
                                           加密每条记录的元数据（sealed metadata）
```

- 云端 `key_vaults` 表为每个用户保存**两个密钥盒**：`password_box`（密码包裹的主密钥）与 `recovery_box`（恢复钥匙包裹的主密钥）。两个盒子都是密文，服务器无法打开任何一个。
- **KDF 已于 2026-07-20 升级为 Argon2id（D-027）**：内存硬函数（64 MiB），GPU 暴力破解成本比旧 PBKDF2 提高 10 倍以上；`libsodium-wrappers-sumo`，`KeyBoxV2` 格式。旧版 PBKDF2 密钥盒（`KeyBoxV1`）仍可打开，并在下次成功解锁时自动**后台无感迁移**：先用新 KDF 重新包裹，验证新密钥盒能正常打开后，才替换旧密钥盒——迁移失败时旧盒保留，用户不会被锁在门外。
- **密码强度强制要求**：最短 8 位，不允许纯数字 / 纯重复字符 / 常见弱密码（`passwordPolicy.ts`）。
- 修改密码 = 用旧密码解出主密钥 → 用新密码重新包裹 `password_box`。**主密钥不变，历史证据无需重加密，纸质恢复钥匙继续有效。**
- 忘记密码 = 用恢复钥匙解出主密钥 → 重设密码、重写 `password_box`。
- 主密钥仅存于会话内存，从不落盘、从不上传；每次页面加载都从锁定状态开始。
- **自动锁定（D-029）**：无交互 10 分钟，或切到后台 ≥3 分钟，内存中的主密钥自动清除，用户需重新输密码。账号登录态保留。
- 解锁密码容忍首尾空白（D-023）：先按原文尝试，失败后 trim 重试；创建密码时即 trim——防止从备忘录粘贴密码时带入不可见空格造成"假锁死"。

### 6.2 文件加密

| 项目 | 参数 |
|------|------|
| 算法 | AES-256-GCM（浏览器 Web Crypto API，`crypto.subtle`） |
| 文件密钥 | 每文件独立生成，256 位 |
| IV | 每次加密随机生成，12 字节 |
| 指纹 | SHA-256 × 2：原文指纹 `originalHash` + 密文指纹 `encryptedHash` |
| 执行位置 | 全部在用户设备浏览器内，**加密先于任何网络调用** |

### 6.3 服务器上只有密文

云端数据结构（Supabase Postgres + Storage，见 `supabase/migrations/0001_key_vault_and_evidence.sql`）：

**`key_vaults` 表** — 每用户一行：`password_box`、`recovery_box`（均为密文 JSON）。行级安全（RLS）：仅本人可读写；**无删除策略**——密钥盒丢失等于证据全失，删除只随账号注销级联发生。

**`evidence_records` 表** — 每证据一行：

| 列 | 内容 | 明文/密文 |
|----|------|----------|
| `tx_id` | 存储对象 ID | 明文（无意义随机 ID） |
| `wrapped_file_key` | 主密钥包裹的文件密钥 | 密文 |
| `encrypted_meta` | 文件名/备注/坐标/设备等 | 密文 |
| `original_hash` | 原文 SHA-256 | **明文**（指纹本身不泄露内容；为将来 TSA 补锚定必须可读） |
| `encrypted_hash` | 密文 SHA-256 | 明文（下载完整性校验） |
| `capture_grade` | 1 现场 / 2 事后 | 明文 |
| `client_time` / `created_at` | 设备时间 / 服务器时间 | 明文（双时间戳） |
| `deleted_at` | 软删除标记 | 明文 |

RLS：所有行仅 `auth.uid() = user_id` 可读写。

**存储桶 `evidence-vault`** — 私有桶（无公开 URL），对象路径 `{auth.uid()}/{tx_id}`，RLS 限定仅路径首段等于本人 UID 者可读写/删除。下载走带鉴权的接口，取回后先校验 `encrypted_hash` 再解密。

### 6.4 双时间戳与可信时间线

每条记录固定两个独立时钟的时间：

- `client_time`：设备时钟（取证瞬间，用户可控设备但改动会与服务器时间矛盾）；
- `created_at`：服务器时钟（上传落库时间，用户不可控）。

两者互为牵制：设备时间早于服务器时间且差值合理，构成"该指纹最迟于服务器时间已存在"的证明基础。`original_hash` 与双时间戳均为明文列，正是为了将来接入权威时间戳（TSA）后可对**历史存量记录批量补锚定**（见第 8 章）。

### 6.5 举证包的独立可验证性

举证包 ZIP 由 `evidenceExport.ts` 在本地生成：解密原件 + 自包含 HTML（无外链、无脚本依赖），验证命令直接印在说明里：

```
Windows:  certutil -hashfile <文件名> SHA256
macOS:    shasum -a 256 <文件名>
```

复算结果与说明中的期望指纹一致，即证明文件与取证瞬间完全一致。验证过程不需要非默应用、不需要网络、不需要任何专有工具。

### 6.6 离线与容错

- 密文常驻 IndexedDB 本地缓存（`the_unmuted_vault`）；
- 断网上传进入 `pending` 队列，`online` 事件触发自动重传，UI 显示"待上传"徽章；
- 下载失败/密文校验失败会明确报错，不会静默展示可疑内容；
- 解锁失败区分两种原因并分别提示（D-023 配套）："保险柜暂时打不开（网络/云端问题，密码未被检验）" vs "密码错误"。

## 7. 隐私与威胁模型

| 威胁 | 对策 |
|------|------|
| **服务器被调取 / 被攻破** | 零知识设计：云端只有密文与无内容含义的指纹。运营方交出全部数据也不泄露任何证据内容、文件名、备注或坐标。 |
| **施暴者拿到手机翻查** | 每次打开应用都处于锁定状态（主密钥只在内存）；10 分钟无操作或后台 3 分钟自动锁定；顶部快速退出按钮可一键切换至无害页面；登录墙外观是普通的密码页，不显示任何内容；紧急求救入口仅为一个无文字的 ‼️ 图标，且陌生设备不显示。 |
| **施暴者胁迫当面删除证据** | 删除界面呈现为立即彻底；实际 72 小时冷静期 + 密码门恢复入口（见 5.8）。 |
| **施暴者胁迫说出密码** | 已知局限，无完美技术对策；纸质恢复钥匙建议存放于施暴者无法接触之处（如信任的亲友处）。 |
| **网络监听** | 全链路 HTTPS；且传输内容本身已是密文，双重保护。 |
| **平台自身作恶 / 消失** | 已导出的举证包用标准格式独立可验证；开发路线上（第 10 章）计划提供全量导出。 |
| **个人身份数据泄露** | 紧急联系人、本地密码等从不上传；服务器仅知邮箱（账号层必需）。设计口径："实名的是账号，加密的是内容"。 |

## 8. 证据效力如何建立（诚实框架）

我们对"证据效力"的表述严格限定在技术事实之内：

**非默当前能够提供的：**
1. **完整性证明**：SHA-256 指纹在取证/导入瞬间固定，任何人可用通用工具复验"此文件自那一刻起未被改动"；
2. **时间线证明基础**：设备 + 服务器双时间戳互为佐证，"该内容最迟于服务器接收时间已经存在"；
3. **来源诚实标注**：现场取证与事后导入明确分级，杜绝"旧图冒充现场"的系统性造假空间；
4. **过程可靠性描述**：加密、哈希、存储、传输方法全部有公开代码与文档可查——这恰是司法解释中电子数据真实性审查所考察的因素。

**非默当前不能、也不对外宣称的：**
1. 不宣称"法院必然采信"——采信由司法机关个案认定；
2. 尚未接入**权威时间戳（TSA）**：当前服务器时间戳来自我们自己的基础设施，证明力弱于国家授时中心背书的 TSA 时间戳。TSA 接入需要公司主体，已列入路线图首位；数据结构（明文指纹 + 双时间戳）已确保接入后**可对全部历史记录补锚定**——今天存的证据，将来同样能获得权威时间戳背书；
3. 不使用"区块链存证"话术：早期演示版的模拟链上锚定已于 2026-07-08 从产品与文案中全面退役。

## 9. 数据存储与合规现状

**如实陈述当前状态（截至本文日期）：**

- 页面静态资源双部署：Vercel（海外）+ **腾讯云 CloudBase（境内）**，境内用户无需任何代理即可访问应用页面；
- 证据密文与账号数据目前存储于 Supabase（境外云服务，底层 AWS）。境内直连当前可用，但跨境链路存在延迟与长期可用性不确定性；
- **既定迁移计划（决策记录 D-016）**：注册公司主体后，将数据后端整体迁移至腾讯云（境内），彻底消除跨境依赖。这被明确定义为**接入真实用户前的硬性前置条件**，而非可选优化；
- 正式上线合规路线（依序）：公司主体注册 → ICP 备案 → App 备案 → 短信签名报备 → 手机号 OTP 登录（实名合规）。设计口径始终是"**实名的是账号，加密的是内容**"——实名要求与端到端加密并不冲突，手机号加密隔离存储，证据内容仍然只有用户本人可解；
- 个人敏感数据（紧急联系人）不入云端，从源头减少合规暴露面。

## 10. 当前局限与路线图

**如实列出的当前局限：**

| 局限 | 影响 | 计划 |
|------|------|------|
| 无权威时间戳（TSA） | 时间证明依赖自有服务器时钟 | 公司主体落地后第一优先级接入，并对历史记录补锚定 |
| 数据后端在境外（Supabase） | 跨境延迟；长期可用性不确定 | D-016 迁移腾讯云，接真实用户前完成 |
| 邮件验证码限额（约 4 封/小时） | 仅够测试期使用 | 接入自定义 SMTP 后解除 |
| 与旧项目共用云项目 | 信任边界不清晰 | 迁移至专用项目（与 D-016 合并执行） |
| 测试覆盖薄弱（23 个单元测试，无 E2E 自动化） | 依赖人工浏览器验证 | 补充 crypto/存证管道单测 + Playwright E2E |

**路线图摘要**（详见 `docs/tasks.md`）：

1. **近期（无前置依赖）**：生物识别解锁（passkey/PRF 包裹主密钥，密码保留为兜底）；全量证据导出；测试补强；
2. **公司主体落地后**：TSA 权威时间戳（含历史补锚定）→ 腾讯云数据迁移 → ICP/App 备案 → 手机号 OTP；
3. **持续**：NGO 审核后台、无障碍审计、多语言扩展。

## 附录 A：术语表

| 术语 | 含义 |
|------|------|
| 端到端加密 | 数据在发送端加密、只在接收端（此处即用户自己的设备）解密，中间任何服务器都无法读取明文 |
| AES-256-GCM | 对称加密算法，256 位密钥，GCM 模式自带完整性校验（密文被篡改会解密失败而非产出错误内容） |
| SHA-256 / 文件指纹 | 哈希算法：对文件计算出 64 位十六进制摘要；文件改动任何一个字节，指纹完全改变；由指纹无法反推文件内容 |
| PBKDF2 | 密钥派生函数：通过大量迭代把密码"拉伸"成加密密钥。保险柜主密钥的派生已升级为 Argon2id（见下）；**举证包一次性密码的派生仍使用 PBKDF2-SHA256（60 万次迭代）**——因为举证包解密工具需要在收件人电脑上零依赖运行，只能用浏览器内置的 Web Crypto API |
| Argon2id | 当前密钥派生算法（2026-07-20 升级，D-027）：内存硬函数（64 MiB），让专用硬件（GPU/ASIC）暴力破解成本大幅提高；现行行业最佳实践 |
| 主密钥 | 每个账户唯一的根密钥，包裹所有文件密钥；本身被密码和恢复钥匙分别包裹后存于云端 |
| KEK | Key Encryption Key，由密码/恢复钥匙派生、专门用于包裹主密钥的密钥 |
| RLS | Row Level Security，数据库行级安全策略：即使持有合法登录态，也只能访问属于自己的行 |
| TSA | Time-Stamping Authority，权威时间戳机构：对"某指纹于某时刻存在"提供有法定效力的第三方背书 |
| 补锚定 | 对历史已存记录的指纹追溯申请权威时间戳（时间效力以补锚定时刻起算，配合原双时间戳形成完整时间链） |
| GCJ-02 | 中国国家测绘局坐标系（火星坐标），境内地图产品通用坐标系 |
| OTP | One-Time Password，一次性验证码 |
